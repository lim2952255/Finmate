# FinMate 포트폴리오·기술 지식 베이스 운영 계획

## 1. 문서의 목적

FinMate의 구현 내용을 Obsidian에 정리하는 가장 중요한 목적은 다음 두 가지다.

1. **장기 복기:** 프로젝트를 떠난 뒤 1년이 지나도 금융 업무 규칙, 설계 판단, 구현 위치, 테스트 근거와 알려진 한계를 빠르게 복원할 수 있어야 한다.
2. **포트폴리오 제출:** 면접관이 FinMate를 통해 일반적인 CRUD 구현뿐 아니라 금융 도메인의 정합성, 트랜잭션, 동시성, 원장, 외부 시세 연동을 어떻게 고려했는지 확인할 수 있어야 한다.

이 두 목적은 필요한 정보의 깊이가 다르므로 하나의 거대한 문서로 합치지 않는다. 내부 복기용 지식층과 외부 제출용 포트폴리오층을 분리하고, 코드·테스트·실행 결과는 별도의 증거층에서 관리한다.

이 문서는 FinMate의 모든 내용을 직접 담는 보고서가 아니다. Obsidian에 **무엇을, 어디에, 어떤 근거와 형식으로 기록하고 계속 갱신할지** 정의하는 운영 기준이다.

## 2. 핵심 작성 원칙

### 2.1 기능 목록보다 판단 근거를 우선한다

“계좌이체를 구현했다”에서 끝내지 않고 다음 질문에 답한다.

- 어떤 금융 문제를 해결하는 기능인가?
- 반드시 지켜야 하는 업무 규칙과 보존식은 무엇인가?
- 왜 해당 트랜잭션 경계와 락 순서를 선택했는가?
- 실패하거나 동시에 실행될 때 어떤 상태가 되어야 하는가?
- 그 계약을 어떤 테스트로 검증했는가?
- 현재 구현에서 아직 해결되지 않은 위험은 무엇인가?

### 2.2 현재 구현과 목표를 구분한다

README나 기획 문서에 적힌 목표가 실제 구현을 의미하지는 않는다. 다음 상태를 명확히 구분한다.

- `implemented`: 현재 소스와 테스트로 확인된 구현
- `in-progress`: 현재 작업 중이며 아직 기준 커밋으로 확정되지 않은 구현
- `known-gap`: 의도한 계약과 현재 구현이 다른 알려진 공백
- `planned`: 앞으로 구현할 계획
- `deprecated`: 더 이상 사용하지 않는 설계나 기능

### 2.3 주장에는 증거를 연결한다

포트폴리오의 모든 기술적 주장은 다음 중 하나 이상으로 확인할 수 있어야 한다.

- 저장소 문서
- 구현 소스 경로 또는 핵심 심볼
- 단위·통합·동시성 테스트
- 테스트 실행 결과
- 재현 가능한 성능 측정
- 명시적으로 표시된 `known-gap` 또는 `planned` 상태

### 2.4 모든 시행착오를 기록하지 않는다

Obsidian을 개발 일지처럼 사용하지 않는다. 단순 문법 오류, 일회성 설정 실수, 재사용할 교훈이 없는 실패는 기록하지 않는다. 이후의 설계나 검증 방식에 영향을 줄 만큼 중요한 판단과 증거만 남긴다.

### 2.5 측정하지 않은 성능은 주장하지 않는다

성능 및 부하 테스트 폴더가 존재한다는 이유로 “성능을 개선했다”고 쓰지 않는다. baseline과 동일 조건 재측정이 있는 경우에만 성능 개선 사례로 승격한다.

## 4. 각 계층의 책임

### 4.1 `00_FinMate_Home.md`

모든 탐색의 시작점이다.

- 프로젝트 한 문장 설명
- 현재 구현 범위와 기준 커밋
- 면접관을 위한 5분 탐색 경로
- 1년 뒤 복기를 위한 상세 탐색 경로
- 핵심 도메인·업무 흐름·규칙·테스트·위험 링크
- 최근 갱신 내용과 현재 작업 상태

Home 문서는 세부 내용을 중복해서 담지 않고 적절한 노트로 안내한다.

### 4.2 `01_포트폴리오/` — 제출용 계층

면접관이 짧은 시간 안에 프로젝트의 가치와 기술적 깊이를 파악하도록 구성한다.

- 무엇을 만들었는가
- 어떤 금융 문제를 고려했는가
- 어떤 선택과 트레이드오프가 있었는가
- 무엇으로 정확성을 검증했는가
- 현재 한계와 다음 개선 방향은 무엇인가

내부 노트를 그대로 복사하지 않는다. 내부 지식층에서 면접 가치가 높은 내용만 `문제 → 고려사항 → 선택 → 증거 → 결과`의 서사로 재구성한다.

### 4.3 `02_내부_지식/` — 복기용 계층

프로젝트를 다시 개발해야 할 때 필요한 핵심 지식을 보존한다. 클래스 하나당 노트 하나를 만들지 않고, 독립적인 의미가 있는 도메인 개념·업무 흐름·업무 규칙·설계 판단 단위로 나눈다.

### 4.4 `03_증거/` — 검증 계층

요구사항, 구현, 테스트와 결과를 연결한다.

- 규칙별 구현 경로
- 테스트 경로와 테스트 수준
- 실행 명령과 결과 요약
- 실패 시 위반된 규칙과 관찰된 상태
- 성능 baseline과 비교 결과
- 포트폴리오 노트로 연결되는 증거

긴 콘솔 출력 전체를 붙이지 않는다. 명령, 종료 상태, 핵심 결과와 원본 위치를 기록한다.

### 4.5 `90_운영/` — 유지보수 계층

기능과 테스트가 계속 추가되어도 동일한 품질로 갱신할 수 있도록 다음을 관리한다.

- 작성 및 공개 안전 원칙
- 중요 정보 편입 기준
- 노트별 템플릿
- 프로젝트 용어집
- 변경 후 업데이트 체크리스트
- 지식 베이스 변경 이력

## 6. 중요 정보 편입 기준

다음 중 하나 이상을 충족하는 내용만 내부 지식층에 추가한다.

1. 금융 업무 규칙 또는 불변식을 결정한 근거
2. 아키텍처·트랜잭션·락·동시성 판단을 바꾼 경험
3. 재현 가능한 장애 또는 측정 가능한 성능 문제와 해결
4. 테스트가 실제 결함을 발견하거나 회귀를 방지한 사례
5. 면접에서 설명할 가치가 있는 트레이드오프·한계·미구현 위험

다음은 기본적으로 기록하지 않는다.

- 단순 CRUD 구현 과정
- 클래스·메서드별 해설
- 문법 오류나 단순 설정 오타
- 재현할 수 없는 막연한 문제
- 교훈이 없는 실패 시도
- 동일한 내용을 여러 폴더에 복제한 문서

## 7. 노트 메타데이터 규칙

모든 FinMate 노트는 최소한 다음 YAML 속성을 사용한다.

```yaml
---
project: finmate
layer: internal
type: process
status: implemented
domains:
  - trading
source_paths:
  - docs/TRADING_FLOW.md
test_paths:
  - src/test/java/com/finmate/service/stock/trading/StockTerminalRaceConcurrencyTest.java
rule_ids:
  - ORD-010
last_verified_commit: "<git-short-sha>"
last_verified_at: YYYY-MM-DD
working_tree_verified: false
portfolio_candidate: true
public_safe: true
tags:
  - finmate
  - 금융불변식
---
```

필드 규칙:

- `layer`: `portfolio`, `internal`, `evidence`, `operations`
- `type`: `overview`, `domain`, `process`, `rule`, `architecture`, `integration`, `test`, `performance`, `decision`, `risk`
- `status`: `implemented`, `in-progress`, `known-gap`, `planned`, `deprecated`
- `source_paths`, `test_paths`: 저장소 상대 경로만 사용
- `last_verified_commit`, `last_verified_at`: 구현 사실을 마지막으로 확인한 기준
- `working_tree_verified`: 커밋되지 않은 작업 트리까지 근거로 삼았는지 표시
- `portfolio_candidate`: 제출층 승격 후보 여부
- `public_safe`: 외부 공개 안전성 검토 결과

## 9. 요구사항·코드·테스트 추적

핵심 연결 구조는 다음과 같다.

```text
포트폴리오 서사
→ 도메인 또는 업무 프로세스
→ 업무 규칙과 금융 불변식
→ 아키텍처 결정
→ 구현 경로
→ 테스트
→ 실행 증거
→ 알려진 위험 또는 성능 지표
```

`03_증거/00_요구사항-코드-테스트_추적표.md`는 다음 형식을 사용한다.

| 규칙·주장 | 업무 프로세스 | 구현 경로 | 테스트 | 상태 | 마지막 검증 | 포트폴리오 링크 |
|---|---|---|---|---|---|---|
| 예수금은 `available + locked = total`을 보존한다 | 주문 접수·취소·체결 | `InvestmentCashBalance` | 관련 단위·통합 테스트 | implemented 또는 known-gap | 커밋·날짜 | 관련 제출 노트 |

근거가 없는 주장은 포트폴리오층에 올리지 않는다. 테스트가 아직 없으면 그 사실을 숨기지 않고 `known-gap`으로 기록한다.

## 10. 정보의 우선순위와 충돌 처리

구현 사실을 판단할 때 다음 순서를 따른다.

1. 현재 소스와 새로 실행한 테스트
2. [FINANCIAL_INVARIANTS.md](FINANCIAL_INVARIANTS.md) 및 적용 가능한 도메인 흐름 문서
3. [ARCHITECTURE.md](ARCHITECTURE.md), [DOMAIN_MODEL.md](DOMAIN_MODEL.md), [TRADING_FLOW.md](TRADING_FLOW.md), [KIS_INTEGRATION.md](KIS_INTEGRATION.md)
4. [PROJECT_OVERVIEW.md](PROJECT_OVERVIEW.md)
5. README의 목표와 설명

문서와 코드가 다르면 하나를 조용히 선택하지 않는다.

- 현재 코드 동작
- 문서가 요구하는 계약
- 차이로 인해 발생하는 위험
- 이를 드러내는 테스트
- 해결 상태

를 함께 기록하고 `known-gap` 또는 `in-progress`로 표시한다.

특히 README에 언급된 JWT, FDS, 뉴스, OpenAI, React, Spring Batch, QueryDSL, AWS 등은 현재 소스와 테스트로 확인되기 전에는 구현 완료로 표현하지 않는다.

## 11. 지속 업데이트 절차

기능, 테스트, 금융 규칙, 동시성 또는 외부 연동이 의미 있게 변경될 때 다음 순서로 갱신한다.

1. **편입 판단:** 변경이 중요 정보 기준을 충족하는지 확인한다.
2. **영향 범위 확인:** 관련 도메인, 프로세스, 규칙, 아키텍처, 테스트 노트를 찾는다.
3. **검증:** 가장 작은 관련 테스트를 실행하고 결과를 확인한다.
4. **내부 지식 갱신:** 관련된 노트만 수정하고 상태·구현 경로·테스트 경로·검증 기준을 갱신한다.
5. **추적표 갱신:** 규칙 또는 주장과 코드·테스트 연결을 수정한다.
6. **포트폴리오 승격 판단:** 문제–판단–증거 서사가 충분할 때만 제출층에 반영한다.
7. **Home 갱신:** 최상위 탐색 경로나 구현 상태가 달라진 경우에만 수정한다.
8. **변경 이력 기록:** 수정한 노트와 검증 결과를 한 줄로 남긴다.
9. **공개 안전 검사:** 비밀정보, 개인정보, 로컬 절대 경로와 검증되지 않은 주장이 없는지 확인한다.

### 11.1 반드시 갱신하는 변경

- 기능 추가·삭제
- 금융 규칙 또는 상태 전이 변경
- 트랜잭션 경계나 락 순서 변경
- 테스트 추가·삭제 또는 새로운 실패
- 재사용 가능한 교훈을 남긴 결함 수정
- KIS·Redis·WebSocket 경계 변경
- 재현 가능한 성능 측정 완료
- 알려진 공백의 발견 또는 해결

### 11.2 갱신하지 않아도 되는 변경

- 포맷팅만 바뀐 코드
- 의미가 달라지지 않는 단순 이름 변경
- 재사용 가치가 없는 문법·설정 실수
- 보호하는 계약과 결과가 동일한 테스트 내부 리팩터링

## 13. 포트폴리오 승격 기준

내부 지식 노트를 포트폴리오층에 반영하려면 다음 조건을 모두 만족해야 한다.

1. 사용자가 맡은 역할과 판단이 명확하다.
2. 금융 도메인 또는 백엔드 설계 역량을 보여준다.
3. 문제 → 선택 → 결과의 인과관계가 있다.
4. 코드, 테스트 또는 측정 근거가 있다.
5. 현재 구현과 목표 상태가 구분된다.
6. 비밀정보나 개인 정보를 포함하지 않는다.

면접관이 5분 안에 다음을 파악할 수 있어야 한다.

- FinMate가 해결하려는 문제
- 실제 구현된 기능 범위
- 예수금 잠금, 원장 원자성, 반올림, 락 순서, 종료 상태 경합 등 주요 금융 고려사항
- KIS·Redis·WebSocket의 역할과 경계
- 테스트 전략과 대표 검증 증거
- 현재 한계와 다음 개선 방향

## 14. 공개 안전 규칙

- API key, secret, password, access token
- 실제 사용자 개인정보나 금융정보
- 세션 ID, 쿠키, 실제 계좌 식별값
- 로컬 컴퓨터의 절대 경로
- 비공개 URL과 내부 서비스 식별자
- 운영 환경 설정값
- 전체 로그나 원본 응답에 포함된 민감정보

저장소 경로는 항상 `src/...`, `docs/...` 형태의 상대 경로로 기록한다.

## 15. 현재 기준에서 반드시 주의할 내용

- FinMate는 KIS 시세를 사용하지만 실제 증권사 주문을 전송하지 않는다. 주식 주문과 체결은 FinMate DB 안에서 처리하는 모의 거래다.
- 테스트가 작업 트리에만 존재하면 커밋된 완료 기능처럼 표현하지 않는다.
- `docs/DEVELOPMENT_GUIDE.md`의 테스트 현황이 현재 소스와 다를 수 있으므로 테스트 관련 노트는 새 실행 결과를 기준으로 작성한다.
- 부분 체결 상태가 존재해도 실제 부분 체결 로직이 완성됐다고 표현하지 않는다.
- 주문 취소·체결·만료 경합과 락 순서처럼 안전성이 완전히 입증되지 않은 내용은 `known-gap`으로 남긴다.
- DB migration, 다중 인스턴스 실시간 fan-out, 운영 배포(CD), 관측성 등 현재 구현되지 않은 범위는 구현 완료 목록에서 제외한다. GitHub Actions CI는 `main` 대상 pull request와 `main` push의 전체 테스트 실행 범위까지 구현되었다.
- 성능 및 부하 테스트는 실제 측정 전까지 계획 상태로 유지한다.

## 16. 완료 기준

Obsidian 초기 정리는 다음 조건을 충족하면 완료로 본다.

1. 모든 FinMate 자료가 `내 포트폴리오/finmate/` 아래에 있다.
2. 하나의 파일이 아니라 포트폴리오·내부 지식·증거·운영 계층으로 분리되어 있다.
3. Home에서 5분 포트폴리오 경로와 상세 복기 경로를 선택할 수 있다.
4. 금융 규칙에서 관련 업무 흐름, 구현 경로, 테스트와 위험까지 이동할 수 있다.
5. 모든 구현 사실 노트에 상태, 검증 커밋과 날짜가 있다.
6. 현재 구현, 작업 중 변경, 알려진 공백과 계획이 구분된다.
7. 내부 지식층에는 중요 정보 기준을 통과한 내용만 있다.
8. 제출층의 모든 주장은 증거가 있고 외부 공개에 안전하다.
9. 성능 개선은 재현 가능한 전후 측정이 있을 때만 주장한다.
10. 기능과 테스트 추가 후 적용할 업데이트 체크리스트가 존재한다.
11. Obsidian 링크가 FinMate 하위 노트 또는 명시된 저장소 상대 경로로 연결된다.
12. 이 문서는 구조와 운영 규칙을 설명하며 실제 포트폴리오 내용을 중복 저장하지 않는다.

초기 지식 베이스를 실제 면접과 장기 복기에 사용할 때는 평면적인 기능 목록보다 하나의 금융 문제를

### 17.1 필수 상세 사례

- 반대 방향 계좌이체와 ID 오름차순 비관적 락

- 실시간 payload 중복 처리와 활성 주문 행 락
- 체결·취소·만료 경쟁 및 현재의 상태 행 잠금 공백
- 전 종목 선적재를 피하는 일봉 on-demand·증분 동기화
- 120일 단위 bounded chunk와 해외 일봉 cursor 진행
- KIS 호출 간격 제한, 재시도, WebSocket 재연결과 구독 참조 수
- `AFTER_COMMIT` 이후 외부 구독 변경과 시작 시 DB 기반 복구
- Redis TTL, JVM 메모리, DB 영속 상태의 책임 분리

### 17.2 금융 원장 표현

FinMate는 애플리케이션 금융 원장을 상태 변경 전에 별도 커밋하는 write-ahead log 패턴을 구현하지 않았다.
잔액의 변경 전 값을 캡처하고, 상태 변경과 영속 원장을 하나의 DB 트랜잭션에 포함하여 모두 성공하거나
모두 롤백한다. JPA `save()` 호출 순서는 실제 SQL flush 순서나 내구성 순서를 의미하지 않는다.

DB 엔진 내부의 WAL·redo log, 애플리케이션 로그, 금융 거래 원장은 서로 구분한다.

### 17.3 사례 노트의 화면 구성

각 상세 사례는 다음 순서를 사용한다.

1. 30초 요약 callout
2. 금융 계약·보호 장치·검증 상태 표
3. 문제가 중요한 이유와 실패 시 사용자 피해
4. 보존식 또는 허용 상태 전이
5. 실제 요청·락·트랜잭션 순서
6. 실패·경합 매트릭스
7. OS·CS 개념과 실제 적용 범위
8. 접힌 구현·테스트 근거
9. 알려진 위험과 다음 검증
10. 예상 면접 질문과 30초 답변

### 17.4 상태 callout

- `summary`: 문제, 선택, 결과와 검증 상태
- `success`: 현재 소스에서 확인된 구현 사실
- `warning`: 테스트 존재 여부와 현재 실행 차단
- `danger`: 락 역전, 멱등성 부재, 미구현 또는 증명되지 않은 보장
- `example`: 긴 구현 경로와 테스트 근거를 접힌 영역으로 제공

### 17.5 OS·CS 개념의 사용 원칙

OS 또는 분산 시스템 개념은 실제 구현과 연결되는 경우에만 사용한다.

- 계좌 ID 오름차순 락: circular wait를 줄이는 전역 자원 순서
- 비관적 락: 금융 행을 보호하는 critical section과 mutual exclusion
- on-demand 일봉 적재: demand paging과 유사한 비용 지연 및 working set 집중
- 120일 chunk: bounded working set과 네트워크 응답 크기 제한
- 구독 참조 수: reference counting과 delayed resource reclamation
- `ConcurrentHashMap`·`AtomicInteger`: JVM 내 concurrent state
- `volatile`, `wait/notifyAll`: WebSocket 연결 상태의 visibility와 조건 대기
- JDK WebSocket `request(1)`: 한 건 단위 수신 제어
- Redis TTL: temporal locality와 stale lifetime 제한

“OS 기능을 직접 구현했다”라고 과장하지 않고 같은 설계 원리를 애플리케이션 경계에 적용했다고 설명한다.
